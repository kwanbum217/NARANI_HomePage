## 질문

이 사이트 dist 산출물에서 Firefox 헤드리스 환경으로 세 가지 인터랙션(모바일 메뉴 토글, 문의 폼 검증과 전송, 요금 포인트 구매 다이얼로그)이 의도대로 동작하는가. 320px 폭에서 8개 페이지가 가로로 넘치지 않는가. 두 번의 실행에서 동일하게 재현되는가.

## 방법

1. 기존 복사본 `/tmp/narani-firefox-interaction-20260927/dist` 와 `BUILD_HEAD.txt`(빌드 커밋 `ee2790e9a0adc4d1d5828e8b1c56b68e6852d92d`)를 그대로 사용했습니다. `dist` 가 이미 존재하여 다시 복사하지 않았습니다.
2. `python3 -m http.server 8922 --bind 127.0.0.1 --directory /tmp/narani-firefox-interaction-20260927/dist` 로 서빙했습니다.
3. Mozilla Firefox 156.0.1 (바이너리 경로 `/Applications/Firefox.app/Contents/MacOS/firefox`)을 `--headless --remote-debugging-port 9922 --profile /tmp/narani-firefox-interaction-20260927/profile` 로 실행했습니다. 원격 제어는 WebDriver BiDi 프로토콜(`ws://127.0.0.1:9922/session`)로 수행했으며, Node 내장 `fetch` 와 `WebSocket` 만 사용했습니다(npm 패키지 설치 없음). Marionette 기본 포트 2828 은 사용하지 않았고, 이미 떠 있는 Firefox 에 붙지 않았습니다. 이전 시도의 Marionette 기반 측정은 잘못된 포트에 붙은 것으로 판명되어 폐기했으며, 그 값은 본 문서에 사용하지 않았습니다.
4. 모든 주소는 `http://127.0.0.1:8922` 만 열었습니다. 각 시나리오와 페이지 측정 전에 `document.querySelector('h1')` 의 텍스트가 이 dist 의 실제 h1 과 일치하는지 확인했고, 불일치 시 그 실행 전체를 폐기하도록 했습니다. 두 실행 모두 h1 확인에서 어긋남이 없었습니다.
5. 인터랙션 시나리오는 `scripts/audit/checks/nav.js`, `scripts/audit/checks/form.js`, `scripts/audit/checks/dialog.js` 의 선택자와 대기 시간을 그대로 사용했습니다. 뷰포트와 페이지는 다음과 같습니다.
   - 메뉴 토글: `/company/`, 390x844
   - 폼 검증과 전송: `/bidbox/contact/`, 1440x1700
   - 요금 다이얼로그: `/bidbox/pricing/`, 1440x1700
6. 화면에 나온 문구는 측정값 그대로 기록했고, 기대한 문구로 바꿔 적지 않았습니다.
7. 320px 넘침은 `scripts/verify.sh` 의 `NARROW` 8페이지(320x900)를 대상으로 `documentElement.scrollWidth` 와 `documentElement.clientWidth`, 그리고 페이지별 콘솔 오류 건수(BiDi `log.entryAdded`, 수준 `error`)를 읽었습니다.
8. 동일한 측정을 두 번 실행하여 원시 JSON 을 `/tmp/narani-firefox-interaction-20260927/run1.json` 과 `/tmp/narani-firefox-interaction-20260927/run2.json` 에 각각 저장했습니다. 두 파일 모두 측정 시각(`measuredAt`)을 포함하며, 두 번째 실행이 첫 번째 파일을 덮어쓰지 않았습니다.
9. 측정 완료 후 자신이 띄운 Firefox 와 HTTP 서버 프로세스만 종료했습니다. 포트 8922 와 9922 에 잔여 리스너가 없음을 확인했습니다. 사용자의 다른 Firefox 는 건드리지 않았습니다.

## 해석

- 세 인터랙션 모두 Firefox 헤드리스에서 의도대로 동작합니다. 모바일 메뉴는 닫힌 상태로 시작해 열고 닫을 때마다 `display` 와 `aria-expanded` 가 함께 바뀝니다.
- 문의 폼은 빈 값 전송을 막고 필드별 오류 문구("성함을 입력해 주세요." 등)를 표시하며, 값을 채우면 오류가 사라지고, 전송 중에는 버튼 문구가 "전송 중…" 으로 바뀌고 `aria-busy=true` 가 설정되며, 완료 후 "접수되었습니다" 문구가 보입니다. 상태를 색만으로 전달하지 않는 디자인 규칙과 일치합니다.
- 요금 페이지에서 포인트 구매 버튼이 다이얼로그를 열고 닫을 수 있으며, 다이얼로그에 표시된 제목과 가격("500포인트 구매", "₩450,000")이 dist 마크업의 실제 문구와 일치합니다.
- 320px 에서 8페이지 모두 가로 넘침이 없고 콘솔 오류도 0건입니다.
- 이전에 기각된 Marionette 측정과 달리, 이번 측정은 각 페이지의 h1 이 이 dist 의 실제 h1 과 일치하는지 확인한 뒤 값을 받았으므로 측정 대상이 이 사이트임이 보장됩니다.
- Chrome 인터랙션 측정 보고서([`크롬_인터랙션_20260926.md`](크롬_인터랙션_20260926.md)) 및 WebKit 기준선([`../context/CURRENT_STATE.md`](../context/CURRENT_STATE.md))과의 비교는 각 문서를 참조합니다.

## 한계

- 본 측정값은 macOS 환경에서 `--headless` 모드의 Mozilla Firefox 156.0.1 로 얻은 결과이며, 일반 창(GUI) 환경의 Firefox 와 동일하다고 단정할 수 없습니다.
- 320px 의 `clientWidth` 값(305 또는 320)은 헤드리스 환경의 세로 스크롤바 폭과 각 페이지 세로 길이에 따라 달라질 수 있는 값입니다. 가로 넘침 판정(`scrollWidth > clientWidth`)은 이 차이와 무관하게 성립합니다.
- 측정은 빌드 커밋 `ee2790e9a0adc4d1d5828e8b1c56b68e6852d92d` 의 dist 복사본을 대상으로 했으므로, 소스 코드를 수정하고 다시 빌드하면 결과가 달라질 수 있습니다.
- 페이지 로드 완료 후 1500ms 를 대기했으나, 웹 폰트나 CDN 자원의 로딩 지연에 따라 다른 환경에서는 타이밍 차이가 발생할 수 있습니다.
- 인터랙션은 `scripts/audit/checks/` 의 시나리오가 다루는 범위(메뉴 토글, 폼 검증과 전송, 다이얼로그 열기와 닫기)만 측정했습니다. 키보드 포커스 이동이나 포인터 좌표 클릭 등의 상호작용은 포함하지 않습니다.
