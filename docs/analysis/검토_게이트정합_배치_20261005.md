## 2. 차단 항목

### B-1. CI 커밋 메시지 검사: 루트 커밋 저장소에서 `git log` 실패가 무음 통과된다

- **위치**: `.github/workflows/ci.yml:67`
- **근거**

  ```yaml
  done < <(git log --format=%H "$range")
  ```

  프로세스 치환(`<(...)`)은 좌변 루프와 **별도 프로세스**로 실행됩니다. 그 안의 `git log` 이 실패(종료 코드 128)해도 `set -euo pipefail` 의 `pipefail` 은 이 프로세스 치환에 적용되지 않고, 루프는 입력이 비었다고 판단한 채 **정상 종료**합니다. 그러면 `failed=0` 이 그대로 남아 `exit $failed` 가 0이 됩니다.

  최초 푸시(all-zeros) 분기(`ci.yml:51-52`)가 정확히 이 경로를 밟습니다. 이 저장소는 최초 커밋 1개뿐인 저장소이므로 `HEAD~1` 이 존재하지 않습니다.

- **재현 명령**

  ```bash
  # 커밋이 1개뿐인 저장소를 만들고 ci.yml 40~68행을 그대로 발라낸 스크립트로 실행
  bash step.sh push "" "0000000000000000000000000000000000000000"; echo "exit=$?"
  ```

  실제 출력(나쁜 메시지로 커밋한 상태):

  ```
  step exit=0
  ```

 stderr 에는 `fatal: ambiguous argument 'HEAD~1..HEAD'` 가 찍히지만 **종료 코드는 0** 입니다. 대조 실험으로 같은 범위를 직접 부르면 `exit=128` 이고, 프로세스 치환 안에 넣으면 루프가 `exit=0` 으로 끝납니다.

- **영향 범위 (좁음)**: 이 저장소의 실제 사용에서는 최초 푸시는 이미 지나갔으므로 `github.event.before` 가 정상 sha 였습니다. 그 경우 `git log` 은 성공하고, 나쁜 커밋이 범위에 있으면 정확히 종료 코드 1 을 냅니다(아래 T7/T8 로 확인). **따라서 지금 당장 이 저장소를 막지는 못합니다.** 다만 게이트가 "최초 푸시·수동 실행"을 검사한다고 주석(`ci.yml:44`, `ci.yml:50`)에 명시한 이상, 그 경로가 조용히 통과하는 것은 오류입니다.

- **권고 수정**: 범위 해석을 루프 밖에서 먼저 검증하거나, `git log` 결과가 비었으면 명시적으로 실패시킵니다.

  ```bash
  shas=$(git log --format=%H "$range") || exit 1
  if [ -z "$shas" ]; then
    echo "검사할 커밋이 없습니다. range=$range" >&2
    exit 1
  fi
  while IFS= read -r sha; do ... done <<< "$shas"
  ```

  이러면 `pipefail` 이 정상적으로 적용되고 빈 입력도 실패로 드러납니다.

### 3. `check-pages-listed.mjs` 의 배열 파싱이 `)` 를 처음 만나면 잘립니다

- **위치**: `scripts/check-pages-listed.mjs:69`
- **근거**


  - 실패로 이어지지 않아 조용히 통과하는 경우는 확인하지 못했습니다. 배열 이름이 바뀌면 `ci.yml` 과 같은 방식으로 명시적으로 실패합니다(`check-pages-listed.mjs:72-74`, 확인: `verify.sh 에서 NARROW 배열을 찾지 못했습니다.` exit=1).
  - 따옴표 없는 항목(`  /|1440x1700`)을 넣으면 해당 항목이 통째로 빠지고 "미검증 페이지"로 드러납니다(조용한 통과는 아님).

### 재현 불가 항목

1. **`.github/workflows/ci.yml:40-68` 커밋 메시지 검사 스텝의 실제 러너 동작.** 이 스텝은 GitHub Actions 러너에서만 실행됩니다. 로컬에서는 `${{ }}` 표현식 확장, `actions/checkout@v7` 의 `fetch-depth: 0` 동작, `github.event.before` 값 주입을 재현할 수 없습니다. 위 T7~T9 는 **셸 로직만** 임시 git 저장소로 모사한 것이며, 러너에서의 관측을 대체하지 않습니다. 위 B-1 은 이 로컬 모사에서 재현된 **셸 레벨** 결함이며, 러너에서도 동일하게 성립하는 판단이지만 러너 확인을 받지는 못했습니다.

2. **`fetch-depth: 0` 이 실제로 필요한지.** 논리적으로는 필요합니다. `checkout` 기본 `fetch-depth: 1` 이면 `github.event.before` sha 가 이력에 없어 `git log "$base..HEAD"` 가 실패합니다. `fetch-depth: 0` 으로 전체 이력을 받아 해결됩니다. 다만 **러너에서 실제로 이 조건을 만들어 보지는 못했습니다.** 논리적 근거로만 채택을 판단했습니다.

3. **CI 의 4단계 정적 검사 6종 전체 통과.** 로컬에서 같은 스크립트 6개를 각각 실행하는 것은 가능하지만, CI 러너(ubuntu-latest, Node 22.18.0, `npm ci`)에서의 통과는 재현 불가입니다. 특히 `check-no-emoji.mjs` 의 파일 수(B-2-2)가 로컬 `.commandcode/taste/` 상태에 따라 달라지는 것처럼, 러너와 로컬의 파일 집합이 다를 수 있습니다.

## 5. 알아낸 사실 중 코디네이터가 놓쳤다고 생각하는 것

1. **`35 files` 는 HEAD 가 아니라 배치 이전 값입니다.** 코디네이터가 재현했다고 하신 `Result (35 files) 0 errors 2 hints` 는 정확히 **0cb8566** 트리에서 나오는 값입니다. HEAD(7a95487)에서는 **37 files** 입니다. 두 스크립트 추가가 `astro check` 대상 파일 수를 올렸기 때문입니다. "같은 값이 재현되는지" 라는 질문의 답은 "재현되지만, HEAD 에서는 다른 값" 입니다. 문서 B-2-1 을 고칠 때 37 로 적어야 합니다.
