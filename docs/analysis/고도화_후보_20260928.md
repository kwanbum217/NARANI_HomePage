## 1. 이 분석의 방법

우선순위를 매기지 않은 권고가 쌓여 실제로 아무것도 안 움직이는 상태를 피하려고
이 문서를 만들었습니다. 각 항목은 실행으로 확인한 값만 적었고, 확인하지 못한
것은 5장에 따로 모았습니다.

검사 방법:

| 영역 | 방법 |
| --- | --- |
| 성능 | Chrome CDP `Performance`/`Network` 엔트리로 LCP 계열 페인트와 리소스 실측 |
| 접근성 | 8개 페이지 전수 DOM 검사(h1 수, heading 순서, 링크·버튼 이름, 라벨, alt) |
| 키보드 | CDP `Input.dispatchKeyEvent` 로 실제 Tab 이동, `:focus-visible` 매칭과 outline 실측 |
| 반응형 | 320px / 753px 에서 `scrollWidth` 대비 `clientWidth` 오버플로우 전수 검사 |
| 구조 | 정본 소스(`src/`)와 게이트 스크립트 대조 |

주의: 접근성 검사 초판에서 "대비 1.00"이 다섯 페이지에서 나왔으나, 이는
검사 코드의 배경색 탐색이 `rgba(0,0,0,0)` 을 걸러내지 못한 **오탐**이었습니다.
같은 항목의 대비는 `docs/analysis/크롬_대비치수_20260927.md` 가 정본입니다.
알려진 오탐을 결론에 포함하지 않습니다.

## 3. 고도화 후보 (우선순위 순)

### 1순위 — 전환 경로에 컨텍스트 손실 (2026-09-28 구현)

`src/pages/bidbox/pricing.astro` 의 주문 확인 다이얼로그가 선택한 상품을
`/bidbox/contact/?plan=<label>` 쿼리로 넘기고, 문의 폼이 그 값을 `values.topic` 으로
받아 "주문 상품" 표시로 보여줍니다. 필수 필드는 늘지 않았으므로 게이트의
`invalidFields === 3` 이 그대로 유지됩니다.

쿼리 값은 `src/data/pricing.ts` 의 `plans` 라벨과 정확히 일치할 때만 받습니다
(`src/scripts/app.js` 의 `PLAN_LABELS`). 화이트리스트가 필요한 이유는 두 가지입니다.
`URLSearchParams` 는 `application/x-www-form-urlencoded` 규칙으로 파싱해
`?plan=a b&c=d` 에서 plan 을 `a b` 까지만 읽습니다. 이 값을 그대로 내보내면 잘린
문자열이 상품명처럼 보이고 `&` 뒤의 내용이 조용히 사라집니다. 주소창을 직접 조작하거나
외부 링크로 유입된 임의 값도 같은 경로로 들어옵니다.

WKWebView 실측(6케이스): `500포인트` 만 표시되고, `a b&c=d`·`<script>alert(1)</script>`·
`500+포인트`·`500`·쿼리 없음은 모두 숨겨집니다.

함정 기록 — `x-data` 안의 `>` 를 쓰지 마십시오. 폰트 서브셋 검사는 태그를 지울 때
첫 `>` 까지만 지우므로, 상태 객체 안의 화살표(`=>`)에서 태그가 끊기고 뒤따르는 코드가
화면 문자로 집계됩니다. 그 코드가 라벨 문자열을 흘려보내면 6단계가 잡아냅니다.
상태 객체 안에는 `function` 을 쓰고, 한국어 설명은 빌드 시 사라지는 자리에 두십시오.
`src/pages/bidbox/pricing.astro` 와 `src/pages/bidbox/contact.astro` 가 그 예입니다.

### 2순위 — 문의 폼 degrade 경로 (2026-09-28 구현)

전송 실패 시 `support@narani.my` 가 주소·`mailto:` 링크·"주소 담기" 버튼으로 보이고,
클립보드 쓰기가 불가능한 환경(보안 컨텍스트 아님)에서는 상태만 실패로 바뀌고
mailto 링크로 내려갑니다. 카피는 `src/data/enquiry.ts` 의 `enquiryFallback` 에
있으며 폼의 `x-data` 는 `src/pages/bidbox/contact.astro` 의 `copyState` 가 따로
스코프를 한 번 더 씌웁니다.

WKWebView 실측: localhost 는 보안 컨텍스트라 담기 버튼이 실제로 동작해
"주소 담기" → "담기 성공" 으로 바뀝니다. http 로 열면 담기가 실패하고
mailto 링크만 남습니다.

### 3순위 — 폰트 서브셋 용량 (2026-09-28 측정 후 반영)

`pretendard-variable-subset.woff2` 가 81,696 바이트에서 52,176 바이트로
29,520 바이트(28.8KB)가 줄었습니다. 10KB 기준을 크게 넘었습니다.

가중치 축을 400~900 으로 좁히고(`src/styles/global.css` 의 `@font-face` 와 일치),
이 사이트가 쓰지 않는 예체(cv01~cv13, ss01~ss08 등)를 제외한 것입니다.
`scripts/build-font-subset.py` 는 fontTools API 로 바꿨고, 서브셋을 먼저 하고
가중치 축을 좁히는 순서를 지킵니다. 순서를 바꾸면 gvar 인스턴싱이 서브셋 글리프와
어긋나 실패합니다.

`tnum` 은 반드시 명시해야 합니다. `global.css` 의 `.num` 이 tabular-nums 를 요청하므로
fontTools 기본값만 쓰면 요금 숫자의 소수점 정렬이 무너집니다.

시각 확인: 8개 페이지 스크린샷을 눈으로 확인했습니다. 네모 □ 로 깨진 글자가 없고
숫자 소수점 정렬이 직선이며, 제목·라벨·본문·강조의 두께 단계가 모두 유지됩니다.
6단계는 "글자가 있다"만 검사하므로 이 확인은 따로 필요합니다.

부수 확인: 세 단위 머지 후 6단계의 검사 문자 수가 352 에서 345 로 줄었는데
두 `dist` 의 문자 집합을 직접 비교해 사라진 문자가 `$;>M{}`(전부 코드 문법)임을
확인했습니다. W1 이 `x-data` 안의 `=>` 를 `function` 으로 바꾼 결과이며,
W1·W2 가 추가한 새 카피 글자는 이미 서브셋에 있었습니다.

## 5. 검증 내역

- 검증한 것(분석 단계, 구현 전): 8개 페이지 성능 실측(3개 상세), 8개 페이지 접근성 전수 검사,
  실제 Tab 키 6회 이동 실측, 320px·753px 오버플로우 전수 검사,
  `dist/` 산출물 메타 태그 전수 확인, `src/` 정본 소스와 게이트 스크립트 대조,
  `npm run verify` 통과(종료 코드 0), `npm run check:emoji` 통과.
- 검증한 것(구현 단계, 병렬 워커 3기): W1·W2·W3 을 별도 worktree 에서 병렬 구현하고
  코디네이터가 파일을 직접 열어 대조한 뒤 단위별로 머지했습니다.
  - W1: WKWebView 로 쿼리 6케이스 렌더 실측. 게이트 8단계 통과(합쳐진 트리에서 재확인).
  - W2: WKWebView 로 에러 패널 표시와 "주소 담기" → "담기 성공" 상태 전이를 실측.
    게이트 8단계 통과, `invalidFields: 3` 유지, 인터랙션 3항목 전부 `fail: null`.
  - W3: 폰트 81,696 → 52,176 바이트 실측. 게이트 6단계 통과. 8개 페이지 스크린샷 육안 확인.
  - 병합 후: 6단계 검사 문자 수 변화를 `dist` 문자 집합 직접 비교로 추적했습니다.
  - 병합 후: `PORT` 를 워커마다 다르게 지정해 포트 충돌을 피했습니다.
- 검증하지 못한 것: **1·2순위의 전환율·클릭률 개선은 여전히 추정입니다.** 구현과
  동작까지 확인했지만, 어떤 수치가 실제로 오르는지는 실사용 GA4 데이터가 있어야 알 수
  있고 배포가 선행되어야 합니다. **3순위의 시각 확인은 macOS WebKit 스크린샷으로만
  했습니다.** Chrome·Firefox·모바일 실사용에서의 폰트 렌더는 확인하지 않았습니다.
  `http` 환경에서 클립보드가 거부되는 degrade 경로도 실제 재현하지 않았고,
  `mailto:` 핸들러가 주소를 여는 것까지는 확인하지 않았습니다.
  접근성 검사 초판의 대비 항목은 검사 코드 오탐이므로 판정에 쓰지 않았습니다.
