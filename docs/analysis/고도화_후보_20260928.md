## 1. 이 분석의 방법

우선순위를 매기지 않은 권고가 쌓여 실제로 아무것도 안 움직이는 상태를 피하려고
이 문서를 만들었습니다. 각 항목은 실행으로 확인한 값만 적었고, 확인하지 못한
것은 5장에 따로 모았습니다.

검사 방법:

| 영역 | 방법 |
| --- | --- |
| 성능 | Chrome CDP `Performance`/`Network` 엔트리로 LCP 계열 페인트와 리소스 실측 |
| 접근성 | 8개 페이지 전수 DOM 검사(h1 수, heading 순서, 링크·버튼 이름, 라벨, alt) |
| 키보드 | CDP `Input.dispatchKeyEvent` 로 실제 Tab 이동, `:focus-visible` 매칭과 outline 실측 |
| 반응형 | 320px / 753px 에서 `scrollWidth` 대비 `clientWidth` 오버플로우 전수 검사 |
| 구조 | 정본 소스(`src/`)와 게이트 스크립트 대조 |

주의: 접근성 검사 초판에서 "대비 1.00"이 다섯 페이지에서 나왔으나, 이는
검사 코드의 배경색 탐색이 `rgba(0,0,0,0)` 을 걸러내지 못한 **오탐**이었습니다.
같은 항목의 대비는 `docs/analysis/크롬_대비치수_20260927.md` 가 정본입니다.
알려진 오탐을 결론에 포함하지 않습니다.

## 3. 고도화 후보 (우선순위 순)

### 1순위 — 전환 경로에 컨텍스트 손실

**현상**
`src/pages/bidbox/pricing.astro:165` 의 "문의로 접수" 버튼은
`/bidbox/contact/` 로 이동만 합니다. 사용자가 어떤 상품을 몇 개 샀는지
다시 설명해야 합니다.

**왜 문제인가**
포인트 구매는 이 서비스의 유일한 수익 경로입니다. 지금은 "500포인트 구매" →
contact 페이지 → 상품명 재설명 → 접수 순서로 2단 입력 손실이 생깁니다.
문의 폼에는 상품 선택지가 없습니다. `values.topic` 은 데모 폼(`demo.astro:74`)
에서만 쓰이고 문의 폼에는 대응 UI 가 없어, inquiries 간 구분이 불가능합니다.

**권고**
contact 폼에 선택 항목(포인트 구매)을 넣고, 다이얼로그에서
`/bidbox/contact/?plan=500` 처럼 쿼리로 넘겨 prefill 합니다.
`app.js` 가 쿼리를 읽어 `values.topic` 에 내려주는 방식이면 폼 마크업 변경 없이
끝납니다. GA4 이벤트에도 `plan` 파라미터를 붙이면 어느 상품이 전환되는지
바로 보입니다.

**선택 사항**
문의 폼에 새 필드를 넣으면 검증 게이트의 `invalidFields === 3` 기대값과
필드 개수가 어긋나므로, 게이트 파생(`scripts/audit/expected.mjs`)을 함께
고쳐야 합니다. 쿼리 prefill 방식이면 필수 필드가 늘지 않아 게이트 수정이
불필요합니다. 후자를 권고합니다.

**미검증**
구현하지 않았으므로 전환율 개선 효과는 추정입니다.

---

### 2순위 — 문의 폼이 유일한 전환 수단

**현상**
결제 미연결 상태에서 문의 폼이 사실상 유일한 전환 경로입니다. 그런데
현재는 폼 제출이 900ms 지연 후 성공 화면만 보여줍니다(`app.js:102`).
실패 시 `app.js:114` 가 이메일 주소를 안내하지만, **이메일 주소가
화면에 복사 불가능하게** 표시됩니다.

**권고**
`support@narani.my` 를 버튼 한 번으로 복사되게 하고 `mailto:` 버튼을
병치합니다. 폼이 실패해도 degrade 경로가 명확해야 합니다.

**미검증**
클릭률 개선은 추정입니다.

### 3순위 — 폰트가 용량의 75%

**현상**
`dist/` 360KB 중 `pretendard-variable-subset.woff2` 1개가 80.1KB(22%)입니다.
홈 페이지 전체 요청 106.6KB 중 80KB가 폰트 하나입니다.

**왜 이것이 낮은 우선순위인가**
이미 CDN 의존을 제거해 `font-display: swap` + `preload` 를 걸었고,
실측 FCP 가 36~76ms 라 성능 문제는 아닙니다. 무거운 변형체
(semi-bold 이상)를 더 줄이면 실측 이득이 미미할 수 있습니다.

**권고**
`fonttools` 으로 현재 서브셋에 실제 쓰이지 않는 가중치를 더 잘라
압축률을 한 번만 측정해 보되, 실측 개선이 10KB 미만이면 되돌립니다.
`docs/analysis/번들_20260925.md` 와 같은 방식으로 판단하십시오.

**미검증**
개선 여부를 측정하지 않았습니다.

  실제 Tab 키 6회 이동 실측, 320px·753px 오버플로우 전수 검사,
  `dist/` 산출물 메타 태그 전수 확인, `src/` 정본 소스와 게이트 스크립트 대조,
  `npm run verify` 통과(종료 코드 0), `npm run check:emoji` 통과.
- 검증하지 못한 것: **1~3순위 후보는 모두 구현하지 않았습니다.** 전환율·클릭률
  개선은 근거 없는 추정이며, 3순위의 폰트 압축률도 측정 전입니다.
  접근성 검사 초판의 대비 항목은 검사 코드 오탐이므로 판정에 쓰지 않았습니다.
  실사용 브라우저(Chrome·Safari·모바일)에서 아직 확인하지 않았습니다.
  실사용 GA4 데이터로 무엇이 개선됐는지 검증하려면 배포가 선행되어야 합니다.
