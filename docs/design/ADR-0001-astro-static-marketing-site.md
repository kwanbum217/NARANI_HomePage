# ADR-0001. 마케팅 사이트를 Astro 정적 사이트로 구현한다

> **작성일**: 2026-09-23
> **상태**: 채택
> **결정자**: 담당자
> **관련 문서**: [`DESIGN_SYSTEM.md`](DESIGN_SYSTEM.md), [`../spec/CONTENT_MODEL.md`](../spec/CONTENT_MODEL.md)

---

## 1. 배경

이 사이트는 회사의 대표 마케팅 홈페이지이며 앞으로 계속 커집니다. 브랜드가 자라면서
로고, 회사명, 내비게이션, 요금, 연락처가 바뀔 때마다 고칠 곳이 늘어나는 것이 원래
문제였습니다.

최초 구현은 순수 HTML 7개 파일이었고, 다음과 같은 비용이 실측되었습니다.

| 문제 | 실측 |
| --- | --- |
| 헤더·푸터가 페이지마다 복제 | 내비 링크 터치 타겟을 42px 에서 44px 로 고치는 데 6개 파일 동시 수정 |
| 데이터가 마크업에 하드코딩 | 요금 3종이 요금 페이지만이 아니라 랜딩과 내비에도 산재 |
| 스타일이 CDN 의존 | 빌드 시점 최적화 없음. 콘솔에 프로덕션 비권장 경고 발생 |
| 연락처 중복 | 이메일이 문의 페이지, 폼 오류 문구에 각각 존재 |

---

## 2. 결정

마케팅 사이트를 **Astro 정적 사이트**로 구현하고, 빌드 산출물은 지금과 같은 순수
정적 HTML 로 유지합니다.

| 항목 | 결정 |
| --- | --- |
| 프레임워크 | Astro 7, `output: static` |
| 스타일 | Tailwind CSS 4 를 Vite 플러그인으로 컴파일 |
| 인터랙션 | Alpine.js 3, 사용 지점 3개소로 제한 |
| 콘텐츠 | TypeScript 데이터 모듈 (`src/data/`) |
| 서버 | 두지 않음 |

---

## 3. 검토한 대안

| 대안 | 채택 여부 | 근거 |
| --- | --- | --- |
| 순수 HTML 유지 | 기각 | 복제 비용이 페이지 수에 비례해 증가. 실측된 6파일 동시 수정 사례 |
| Next.js + React | 기각 | 이 사이트의 인터랙션은 3개뿐. React 런타임을 얹으면 얻는 것이 없고 번들·빌드 복잡도만 증가 |
| Eleventy | 기각 | 컴포넌트 스코프 스타일과 콘텐츠 컬렉션이 약함. 성장하는 사이트에 필요한 기능이 부족 |
| 제품 본체(FastAPI + Jinja)에 편입 | 보류 | partials 문제는 해결되나 정적 배포 이점을 잃음. 결제·포인트가 이 저장소 범위에 들어오면 재검토 |
| Astro | **채택** | 기본 클라이언트 JS 0, 컴포넌트·레이아웃·데이터 단일 소스, 산출물은 정적 HTML |

Astro 를 React 와 동일시하지 않습니다. Astro 는 프레임워크 런타임을 기본으로 싣지
않으며, 필요해지면 특정 위젯만 아일랜드로 React 를 넣을 수 있는 여지를 남깁니다.

---

## 4. 결과

좋아진 것:

- 브랜드 변경 시 수정 지점이 `site.ts`, `pricing.ts`, `Logo.astro`, `global.css` 로 고정됨
- 페이지 추가가 파일 1개 추가로 끝나고, 헤더·푸터·메타가 자동 상속됨
- Tailwind 컴파일로 CDN 경고가 사라지고 빌드 시점 최적화가 적용됨
- 검증이 자동화됨. `npm run verify` 가 렌더·접근성·인터랙션을 실측

감수한 것:

- 빌드 단계가 생김. 폴더를 직접 열어 확인할 수 없고 `npm run dev` 또는 빌드가 필요함
- Node 의존성이 생김. `package-lock.json` 으로 고정해 재현성을 확보
- 검증 도구가 macOS WebKit 기반이라 CI 에서 전부 돌지 않음. CI 는 빌드와 링크
  무결성만 검사하고, 브라우저 검증은 로컬에서 수행

---

## 5. 재검토 조건

다음 중 하나가 참이 되면 이 결정을 다시 엽니다.

1. 로그인, 결제, 포인트 지급 등 서버 상태가 이 저장소 범위에 들어온다
   (이 경우 서버를 새로 만들지 않고 제품 본체로 위임하는 안을 먼저 검토)
2. 다국어가 필요해진다 (Astro i18n 라우팅으로 대응 가능하나 구조 변경 필요)
3. 페이지 수가 20개를 넘어 콘텐츠 관리가 필요해진다 (헤드리스 CMS 검토)
