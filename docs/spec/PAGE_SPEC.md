## 2. `/` 접속페이지

**목적**: 도메인 최초 진입에서 회사와 제품 중 하나를 즉시 고르게 합니다.
**대상**: 처음 방문한 잠재 고객. 회사와 제품이 같은 도메인에 있다는 사실을 모릅니다.

| 순서 | 섹션 | 내용 |
| --- | --- | --- |
| 1 | 히어로 | 라벨 `Narani · Bidbox`, 제목 `나란히, 더 나은 결정을 위해`, 안내문 |
| 2 | 선택 카드 2장 | 좌측 회사소개(라이트), 우측 BIDBOX(다크) |
| 3 | 특화 분야 안내 | 용역 분야 특화 문장 |

**상태**: 링크만 존재합니다. 로딩·오류 상태가 없습니다.
**수용 기준**

- 두 카드가 각각 `/company/`, `/bidbox/` 로 이동합니다.
- 라이트 카드와 다크 카드가 첫 화면에서 동시에 보여 두 표면의 성격을 전달합니다.
- 320px 에서 카드가 세로로 쌓이고 문서 오버플로우가 없습니다.

## 3. `/company/` 회사소개

**목적**: 회사의 태도와 만드는 것을 전달합니다.
**대상**: 회사를 먼저 확인하려는 방문자, 채용·제휴 검토자.

| 순서 | 섹션 | 내용 |
| --- | --- | --- |
| 1 | 도입 | 태그라인, 회사 정체성 문장 |
| 2 | 3원칙 | `같은 눈높이`, `근거를 곁에`, `그 자리에서 결정` |
| 3 | 만드는 것 | BIDBOX 소개와 개념 요약 블록 |
| 4 | 마무리 CTA | 데모 신청, 문의하기 |

**상태**: 정적입니다. 3장의 개념 요약 블록은 가로 스크롤 컨테이너입니다.
**수용 기준**

- 태그라인이 원본 슬라이드 2와 일치합니다.
- 3원칙 문장이 원본 슬라이드 3의 문장을 나눈 것이며 의미가 변하지 않습니다.
- 개념 요약 블록이 320px 에서 문서 폭을 밀지 않습니다.

## 4. `/bidbox/` BIDBOX 랜딩

**목적**: 제품을 처음 보는 사람에게 가치와 근거를 한 화면에 제시합니다.
**대상**: 입찰 담당자, 용역 기업 대표.

| 순서 | 섹션 | 내용 |
| --- | --- | --- |
| 1 | 히어로 | 라벨 `용역 분야 전문`, 제목, 부제, 행동 2개 |
| 2 | 예측 결과 예시 | 공고, 예상 낙찰금액, 기초금액, 예상 낙찰률 카드 |
| 3 | 핵심 기능 3종 | `capabilities` 데이터에서 렌더 |
| 4 | 상세 이동 | 서비스 페이지 링크 |

**상태**: 정적입니다. 히어로의 예측 예시는 실제 데이터가 아닌 예시 값이며, 그 사실을
카드 하단 문장으로 명시합니다.
**수용 기준**

- 예측 예시임을 오해하게 하는 표현이 없어야 합니다.
- 핵심 기능 3종이 `src/data/site.ts` 의 `capabilities` 에서 렌더되고, 서비스 페이지와
  같은 값을 씁니다.

## 5. `/bidbox/service/` 서비스

**목적**: 무엇을 어떻게 예측하는지, 어떤 분야에 특화됐는지 납득시킵니다.

| 순서 | 섹션 | 내용 |
| --- | --- | --- |
| 1 | 도입 | 제목, 시장 불확실성 최소화 설명 |
| 2 | 핵심 기능 3종 | 아이콘 포함. `capabilities` 에서 렌더 |
| 3 | 예측 방식 | `단순 정보 제공이 아니라 AI가 예측한 결과를 제공합니다`, 특화 분야 |
| 4 | 대상별 이득 2종 | `경력 없이도 손쉬운 입찰`, `전문가는 더 정확하게` |
| 5 | 마무리 CTA | 데모 신청, 요금 보기 |

**상태**: 정적.
**수용 기준**

- 특화 분야 표기가 `근로자파견 · 경비업 · 위생관리용역업 · 직업소개업` 으로 원본과
  일치합니다.
- 3장의 카드 아이콘이 `capabilities` 의 `icon` 필드에서 오며 마크업에 복제되지 않습니다.

## 6. `/bidbox/pricing/` 요금

**목적**: 요금 구조를 숨김 없이 제시하고 구매 의사를 접수합니다.

| 순서 | 섹션 | 내용 |
| --- | --- | --- |
| 1 | 도입 | 제목, 비용 효율 안내 |
| 2 | 단가 안내 | `1포인트 1,000원`, 사용 규칙, 재조회 차감 유의 |
| 3 | 요금제 3종 | `src/data/pricing.ts` 에서 빌드 타임 렌더 |
| 4 | 주문 확인 다이얼로그 | 선택 요금제 요약, 결제 예정 금액, 안내 |

**상태**

| 상태 | 동작 |
| --- | --- |
| 기본 | 요금제 카드 3장, 다이얼로그 닫힘 |
| 카드 선택 | 다이얼로그 열림, 제목과 금액이 선택에 따라 변경 |
| 닫기 | 다이얼로그 닫힘, 포커스가 트리거로 복귀 |

**수용 기준**

- 금액이 `src/data/pricing.ts` 에서만 옵니다. 마크업에 금액 리터럴이 없습니다.
- 할인 표시가 있는 요금제만 할인가와 정가를 함께 보여 줍니다.
- 결제 미연결 상태를 숨기지 않고 다이얼로그 안에서 명시합니다.

**미완**: 실제 결제 이동. 제품 본체의 결제 라우트로 연결해야 합니다.

## 7. `/bidbox/demo/` 데모 신청

**목적**: 관심 공고 1건을 받아 데모로 연결합니다.

| 순서 | 섹션 | 내용 |
| --- | --- | --- |
| 1 | 안내 | 제목, 데모에서 보여 줄 것 3가지 |
| 2 | 신청 폼 | 회사명, 이메일, 관심 공고(선택), 확인하고 싶은 내용 |

**상태**

| 상태 | 동작 |
| --- | --- |
| 기본 | 폼 표시, 제출 버튼 활성 |
| 검증 실패 | 실패한 필드에 메시지 표시, 제출 버튼은 계속 활성 |
| 입력 수정 | 해당 필드 오류 즉시 해제 |
| 전송 중 | 버튼 라벨 `신청 접수 중…`, `aria-busy=true`, 버튼 비활성 |
| 성공 | 성공 패널, 입력한 이메일 안내, 재작성 버튼 |
| 실패 | 오류 메시지, 재시도 안내 |

**수용 기준**

- 필수 항목은 회사명, 이메일, 확인하고 싶은 내용입니다.
- 제출 버튼은 폼이 유효해질 때까지 비활성화하지 않습니다. 비활성 버튼은 고쳐야 할
  항목을 숨깁니다.
- 라벨은 항상 보이며 placeholder 를 라벨로 쓰지 않습니다.

**미완**: 실제 전송. `enquiryForm(endpoint)` 에 엔드포인트를 주입해야 합니다.

## 8. `/bidbox/contact/` 문의

**목적**: 상담 요청을 접수합니다.

| 순서 | 섹션 | 내용 |
| --- | --- | --- |
| 1 | 도입 | 제목, 상담 안내 |
| 2 | 연락처 | 이메일, 채팅 상담 안내 |
| 3 | 문의 폼 | 성명, 이메일, 문의내용 |

**상태**: 데모 신청과 동일한 `enquiryForm` 을 사용합니다.
**수용 기준**

- 이메일이 `src/data/site.ts` 의 `brand.email` 에서 오고, `mailto` 링크와 표시 텍스트가
  같은 값을 씁니다.
- 이메일은 현재 오타 의심 항목입니다. 확정 전까지 원본 표기를 유지합니다.

**미완**: 실제 전송.

## 10. 페이지 추가 절차

1. 이 문서에 항목을 추가합니다.
2. `src/pages/` 에 파일을 만들고 `BaseLayout` 을 사용합니다.
3. 내비에 노출해야 하면 `src/data/site.ts` 의 `siteNav` 또는 `productNav` 에 추가합니다.
4. 반복되는 카피가 있으면 `src/data/` 로 올립니다.
5. `scripts/verify.sh` 의 `PAGES` 목록에 새 라우트를 추가합니다.
6. `npm run verify` 를 실행합니다.

상세 절차는 `.agents/skills/page-authoring/SKILL.md` 를 따릅니다.
